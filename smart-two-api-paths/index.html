SMART: Two API Paths

A practical walkthrough of why SMART supports two distinct integration patterns: a browser-driven path for SMART UI users and a server-to-server path for PET.

Instructional video · architecture, identity, TLS and API flow View full video
The core idea

Same SMART capability. Different trust boundaries.

The two paths should not be forced into one identical pattern. Browser users and backend applications have different identities, different token issuers, and different gateway requirements.

Path 1 — SMART UI

A human user accesses the SMART web application. Browser authentication establishes the user session, and the UI calls the SMART backend through the application’s own web tier.

Browser→ Web / Auth Layer→ SMART UI→ SMART API

Path 2 — PET → SMART API

PET is an application-to-application integration. Its backend obtains a service token and calls SMART through the enterprise API path where gateway policy validates the request before it reaches SMART.

PET Backend→ Cloud Identity→ API Gateway→ SMART API
Design implications

What the distinction changes

IdentityThe UI represents an interactive user. PET represents a calling application/service.
Gateway roleThe external application path benefits from centralized API policy, token validation, routing and observability.
TLSEach network hop protects transport independently; termination points depend on the concrete deployment boundary.
AuthorizationAuthentication proves who or what is calling. Authorization still determines which SMART capabilities that identity can use.
TraceabilityCorrelation identifiers make multi-hop requests easier to trace across gateways, web tiers and backend services.
Separation of concernsBrowser SSO and machine-to-machine API access solve different problems and should remain architecturally explicit.

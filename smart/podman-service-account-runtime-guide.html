SMART · Production Runtime Architecture

Podman, Service Accounts, nginx & Identity Separation

How to move SMART API from a developer-owned rootless Podman container to a stable production service identity—without mixing Linux runtime identity, container identity, downstream workload credentials, or application-user authentication.

1. Runtime identity should not be a person

Your current setup can work technically, but production lifecycle should not depend on your personal Linux identity. People leave, accounts are disabled, permissions change, passwords/MFA policies change, and audit ownership becomes ambiguous.

Recommended: your personal account stays the human/operator identity; a dedicated SMART service account owns rootless Podman runtime state; systemd/Quadlet manages startup, restart and recovery.

The production fix is not merely “log in as the SA and run the same podman run command.” The stronger model is rootless Podman + systemd/Quadlet + non-interactive service identity.

2. Will the annual SA password change stop SMART?

Normally, no. Linux does not continually re-authenticate a running process with the account password. Once Podman is started under the SA’s UID/GID, the kernel tracks processes using that identity.

Key point: SA password ≠ container runtime secret.

A CyberArk password rotation should not kill an already-running container, and a properly managed systemd service should not need the SA password embedded anywhere for ordinary startup.

Exception: if SMART itself uses that password to authenticate to SQL Server, a network share or another system, rotation could affect that dependency. That is workload authentication, not Podman runtime authentication.

3. Not being able to su to the SA may be intentional

Many production service identities deliberately use /sbin/nologin or /bin/false. That is often desirable.

getent passwd <service-account>
id <service-account>

The more important question is whether the account has a persistent location for rootless Podman storage/configuration and the required user-namespace mappings.

Do not ask for interactive login just because Podman needs to run. Ask infrastructure for the runtime prerequisites instead.

4. What privileges does the SA need?

# Compare identity and rootless mappings
id <sa>
getent passwd <sa>
grep "^<sa>:" /etc/subuid
grep "^<sa>:" /etc/subgid

# Your current working setup
id
grep "^$(whoami):" /etc/subuid
grep "^$(whoami):" /etc/subgid
podman info --debug
podman info --format '{{.Store.GraphRoot}}'
sudo -l

The SA generally needs a valid UID/GID, rootless Podman prerequisites, subordinate UID/GID mappings, persistent writable Podman storage, only the filesystem access SMART actually needs, approved secret/certificate access, network access to dependencies, and systemd user/Quadlet support if that is the lifecycle model.

It should not simply inherit your entire developer privilege set.

5. Does the SA need the CTCore Linux group?

Only if a specific runtime resource requires that group. “My account is in CTCore, therefore the SA should be” is weak reasoning.

id
id <sa>
getent group CTCore
ls -ld /path/to/smart
namei -l /path/to/smart/backend/something
getfacl /path/to/smart

If CTCore grants only access SMART needs, membership may be fine. If it grants broad developer or operational permissions, prefer an app-specific group or ACL.

6. Does the SA need sudo nginx -t or reload?

Usually no. Those are operator/deployment authorities, not runtime privileges.

Human/operator

Deploy approved artifacts
nginx validation/reload if authorized
Trigger restart
Inspect logs/status

SMART service account

Own Podman runtime state
Run SMART API
Read only required files/secrets
No general sudo

Giving a rootless runtime identity broad sudo partly defeats the purpose of rootless isolation.

7. Should the SA be able to git pull?

Preferably not. Production runtime identities should consume deployable artifacts, not act like developer workstations.

Git repository │ ▼ Build + test pipeline │ ▼ Immutable SMART API image │ ▼ Artifactory │ ▼ Controlled production deployment │ ▼ systemd / Podman

For React, build the static bundle elsewhere and deploy the compiled artifact for nginx. Avoid unnecessary source-control credentials and build tooling on the production runtime identity.

8. Images are user-specific under rootless Podman

Your existing image is in your rootless Podman storage. A different rootless user normally does not see it.

podman info --format '{{.Store.GraphRoot}}'
podman images

Do not solve this by making two users share one writable Podman graphroot.

Long-term

Give the approved deployment/runtime mechanism read-only Artifactory pull access, ideally through an automation/deployment credential rather than a human identity.

Transitional

# Current user
podman save -o smart-api.tar artifactory/.../smart-api:<tag>

# Approved execution under the SA identity
podman load -i smart-api.tar

That can avoid an immediate new registry integration, but it should not become the permanent release process.

9. What account is the React frontend running as?

If React is deployed as compiled static files, there is no React runtime process. nginx reads index.html, JavaScript and CSS and sends them to browsers.

ps -eo user,pid,ppid,args | grep '[n]ginx'
sudo nginx -T 2>/dev/null | grep -E '^[[:space:]]*user[[:space:]]'
grep -n '^[[:space:]]*user' /etc/nginx/nginx.conf

The static files may be owned by your Unix account because you copied/built them. That does not mean React is “running as you.” File ownership and process identity are different.

10. Keep four identity layers separate

Host runtime identity

svc_smart
Owns rootless Podman processes/storage on Linux.

Container process identity

appuser / internal UID
Runs FastAPI/uvicorn inside the container.

Workload identity

OAuth client, Kerberos principal, DB identity
SMART authenticating to other systems.

Application user

Entra/Cognito human identity
The business user accessing SMART.

These solve different problems and should not be collapsed into one account.

11. Target SMART operating model

User │ ▼ nginx system service ├── serves React static files └── proxies /api │ ▼ localhost:8000 │ ▼ rootless Podman host identity: svc_smart │ ▼ SMART FastAPI container app user

Lifecycle

System boot │ ▼ systemd user manager for svc_smart │ ▼ SMART Quadlet / user service │ ▼ Podman starts SMART API ├── healthcheck └── restart policy
Operational result: nobody logs into the service account after reboot to start SMART.

12. Suggested Linux/infrastructure request

Request:
We are migrating the SMART API from a developer-owned rootless Podman container to a dedicated non-interactive service identity. We do not require interactive SSH access to the service account.

Please confirm/provision: (1) persistent writable home or rootless Podman storage; (2) /etc/subuid and /etc/subgid mappings; (3) ability to run rootless Podman; (4) systemd user/Quadlet support with lingering so SMART starts at boot without interactive login; (5) required access to SMART configuration/volume directories; (6) appropriate SELinux labeling; and (7) a controlled way for operators to start/stop/restart/view logs without knowing or storing the SA password.

Interactive login, broad sudo and Git access are not required.

13. Better bridge from M365/GitHub Copilot to ChatGPT

Screenshots are convenient, but they are not automatically safer. If policy restricts information from leaving the managed environment, a screenshot containing the same information is still a transfer.

A better pattern is to ask the work Copilot to create a sanitized context packet:

Summarize this discussion for an external technical advisor.
Preserve technical architecture, commands, alternatives,
assumptions, unresolved questions and reasoning.

Remove or generalize confidential information, internal hostnames,
usernames, account numbers, client IDs, secrets, tokens, URLs,
business data and proprietary identifiers.
ENVIRONMENT
RHEL shared application server
Rootless Podman
nginx reverse proxy
React + FastAPI

CURRENT STATE
Developer owns current Podman container.
New non-interactive SA has been provisioned.

COPILOT ANSWER
[sanitized summary]

COMMAND OUTPUT
id <redacted>
podman info <sanitized>
systemctl status <sanitized>

OPEN QUESTIONS
1. SA has no home.
2. SA cannot log in interactively.
3. Need subuid/subgid validation.
4. Need Podman storage decision.

Preserve structure but replace sensitive identifiers with placeholders such as APP-SERVER, SMART-SA, ARTIFACTORY-URL, SMART-DB and <REMOVED>.

Immediate validation checklist

id

Those outputs will isolate whether the remaining gap is identity provisioning, rootless Podman prerequisites, storage, filesystem permissions, SELinux or operational control.

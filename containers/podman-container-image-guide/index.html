Container Image vs Container

A practical mental model for understanding container state, persistence, snapshots, portable images, volumes, and reproducible deployment.

1. Core mental model

ImageA reusable blueprint built from read-only filesystem layers plus metadata.
ContainerA running or stopped instance of an image, with an additional writable layer.
IMAGE                         CONTAINER
─────                         ─────────
Blueprint / template          Instance created from blueprint
Read-only layers              Image + writable layer
Reusable                      Has runtime state
Creates many containers       Usually disposable / recreatable

      podman run
Image ───────────────► Container
                          │
                          │ podman commit
                          ▼
                      New Image
Remember:
Image = what the application should be.
Container = one execution of that image.
Volume = data that should survive the container.

2. Can a container be saved?

Yes. But “save” can mean several different things.

A. Stop it and restart it later

podman stop demo-app
podman ps -a
podman start demo-app

A stopped container still exists unless it was created with --rm. Changes in its writable layer remain.

podman ps = running containers
podman ps -a = running + stopped containers

3. Convert a container into a new image

Suppose a container is started from myapp:v1 and modified interactively:

podman run --name myapp myapp:v1
podman exec -it myapp bash

# Example changes inside the container
dnf install ...
vi /etc/myapp/config
pip install ...

Those changes live in the container's writable layer. Capture them as a reusable image with:

podman commit myapp myapp:v2
podman images
Image v1
   │ podman run
   ▼
Container
   ├── changed config
   ├── installed package
   └── new files
   │
   │ podman commit
   ▼
Image v2
podman rm myapp
podman run --name myapp2 myapp:v2
Use commit carefully: it is valuable for debugging, emergency snapshots, and preserving ad-hoc changes. It is usually a poor primary production build process because the result is harder to reproduce and audit than a Containerfile.

4. Save an image to a portable TAR file

podman save -o myapp-v2.tar localhost/myapp:v2

Copy the archive to another host and load it:

scp myapp-v2.tar other-server:/tmp/
podman load -i /tmp/myapp-v2.tar

This is useful where a container registry is unavailable or where image movement must happen through controlled file transfer.

6. The major trap: volumes

podman run   -v /data/demo-app:/app/data   app-api:v1
┌────────────── Container ──────────────┐
│ /app/code                            │
│ /usr/lib/...                         │
│                                      │
│ /app/data ──────────────┐            │
└─────────────────────────│────────────┘
                          ▼
                    Host /data/demo-app

Mounted volume or bind-mount data lives outside the container's normal writable layer. A committed image is therefore not a complete backup of the application's persistent data.

Image should containApplication code, dependencies, OS packages, runtime, and safe default configuration.
External persistence should containDatabases, persistent files, uploaded content, important logs, environment-specific data, and secrets managed outside the image.

7. Recommended production pattern

Prefer reproducibility over preserving hand-edited containers.

Recommended: build a reproducible image, keep persistent state outside the container, and use systemd/Quadlet so the service starts predictably after host reboots.

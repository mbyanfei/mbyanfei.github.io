Agentic Engineering • GitHub Copilot

What are we actually building?

A thin agentic engineering workflow layer on top of the GitHub Copilot agent harness. Copilot supplies the execution machinery; our layer defines how engineering work should be explored, planned, implemented, verified, reviewed, and resumed.

Short version: GitHub Copilot is the harness. Our /ship, /design, custom agents, and SPEC/PLAN/STATUS files form the workflow and lightweight orchestration layer.

The terminology

LLM / model

The reasoning engine

The model interprets the goal, reasons about the code and architecture, proposes changes, and decides which tools to use.

Agent harness

The execution environment

The harness turns the model from a chatbot into a working engineering agent by giving it repository context, tools, file editing, shell access, Git operations, subagents, hooks, and integrations.

Workflow layer

How work should proceed

Our layer imposes just enough discipline: explore, specify, plan, implement, verify, review, and persist the state needed to resume later.

Skills + agents

Reusable capabilities

Skills such as /ship encode repeatable workflows. Specialist agents such as architect and verifier are delegated to only when they add value.

Artifacts / state

Durable engineering memory

SPEC.md, PLAN.md, and STATUS.md preserve intent, execution plan, decisions, risks, and progress outside a single chat session.

Repository

The actual work surface

Source code, tests, configuration, APIs, schemas, documentation, and Git history remain the system of record for the software itself.

What exactly is a harness?

The harness is the machinery around the model that lets it act. The model alone can reason and generate text. The harness gives it the controlled ability to inspect and modify a real engineering environment.

Model says: “I need to inspect the authentication code.”
        ↓
Harness reads repository files
        ↓
Model reasons about the implementation
        ↓
Harness edits Python / TypeScript / SQL
        ↓
Harness runs tests or shell commands
        ↓
Model inspects failures
        ↓
Harness applies another change
        ↓
Git diff + verification

That model–tool–observation loop is what makes an AI coding agent materially different from a plain chat interface.

Small fixes should create none of these. The artifacts exist only when persistent context is worth the overhead.

Lightweight orchestration, not an orchestration engine

Our main Copilot agent can delegate architecture or independent verification, but we are deliberately not building a scheduler, queue, daemon, worker pool, state machine, or multi-agent runtime.

Main Copilot Agent
       │
       ├── architect   → only when architecture decisions matter
       │
       ├── implementation stays with the main agent
       │
       └── verifier    → independent acceptance check when useful

This is orchestration in the small: selective delegation inside a workflow. GitHub Copilot remains responsible for actual agent execution.

Why this is different from GSD, FirstMate, and SPD

FirstMate

Closer to an orchestration layer

FirstMate coordinates multiple coding-agent harnesses and adds multi-agent execution behavior. It owns substantially more of the runtime and delegation model.

GSD

Structured workflow system

GSD adds a stronger methodology around planning, persistent context, lifecycle phases, verification, and agent orchestration. Powerful, but heavier.

SPD

Specification-driven workflow

SPD is closer to Markdown-first process and task structure, with small helpers around planning, implementation, and engineering state.

Our approach

Use the harness we already have

Copilot already provides execution. We add only the missing control layer: engineering workflow, selective delegation, explicit acceptance criteria, and compact persistent state.

Data-platform analogy

For a data/AI engineer, this mapping is useful:

LLM                         ≈ compute engine
GitHub Copilot Agent        ≈ execution platform
/ship workflow              ≈ orchestration DAG
Skills / custom agents      ≈ reusable operators
SPEC / PLAN / STATUS        ≈ control + state tables
Git repository              ≈ working data + system of record

The analogy is not perfect, but it highlights the architectural boundary: we are defining orchestration and state without rebuilding the underlying execution platform.

The design principle

Use Copilot for execution. Add only enough workflow to improve engineering quality and continuity.
Persistent context Disciplined planning Architecture when needed Implementation Verification Independent review

The main failure mode to avoid is gradually adding enough agents, lifecycle stages, hooks, files, MCP servers, and policies that the “lightweight” layer becomes another full framework.

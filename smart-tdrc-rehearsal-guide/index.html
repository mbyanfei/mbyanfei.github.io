SMART TDRC Rehearsal Guide

Prepared for the SMART solution architecture review — September 11, 2026

This is the consolidated rehearsal script from our mock TDRC session. It is optimized for concise verbal answers, with deeper technical notes underneath so you can review the concepts before the meeting.

1. Two-Minute Architecture Overview

Use this answer:

“SMART has two entry points: the browser UI and PET.

For the SMART UI, the path is browser to Nginx as the ingress boundary, then React to FastAPI to SQL Server. Users authenticate with Microsoft Entra using MSAL and Authorization Code Flow with PKCE. The React SPA has no client secret. Entra issues the access token, and the SMART API validates the token and enforces authorization.

For PET, the path is PET backend to cNLB to APIC, which is the network and policy boundary, then to the SMART API and SQL Server. PET uses a Cognito-issued workload token. APIC validates the token and applies policy before forwarding the request.

The key open dependencies are APIC and network readiness for the PET path, and production/DR operational maturity.”

2. Authentication and Authorization

SMART UI

  • Issuer: Microsoft Entra
  • Client: React SPA using MSAL
  • Flow: Authorization Code + PKCE
  • Client secret: None in the SPA
  • Validator: SMART API
  • Authorization: scopes and/or app roles

PET

  • Issuer: AWS Cognito
  • Identity: PET workload identity, not the human user
  • Validator: APIC
  • Authorization: gateway policy using token claims/scopes
  • User delegation: not required initially

Recommended TDRC phrasing

“The identity provider issues the access token. The receiving API or gateway validates it, and then authorizes based on claims such as scopes or roles, depending on the design.”

Scopes vs roles

  • Scope: what API access has been granted, e.g. smart.read or smart.write.
  • App role: what kind of SMART user this is, e.g. Reader, Editor, Admin.
  • Claim: a general field inside the JWT payload. Scopes and roles are examples of claims.

Do not say scopes and roles are the same thing. If all users have identical rights at launch, keep roles simple or defer them until there is a real separation-of-duties requirement.

3. JWT Validation — Deep Technical Backup

“The SMART API uses an approved JWT/OIDC validation library integrated with Entra metadata. It verifies the token signature using Entra’s published public keys, checks issuer, audience, expiration, and then enforces scopes or roles. Missing or invalid token returns 401; valid token without permission returns 403.”

  • The HTTP Authorization header carries Bearer <access_token>.
  • The bearer token is typically a JWT.
  • The JWT contains its own header, payload, and signature.
  • The payload contains claims.
  • Entra signs with its private key.
  • The API validates using Entra’s published public keys/JWKS.
  • The JWT header contains a kid that identifies which public key to use.
  • PKCE happens earlier, when the SPA securely acquires the token. JWT validation happens later, when the API receives it.

4. Why PET Still Needs Authentication if the PET User Already Logged In

“PET user login and PET application authentication are two separate things. The user authenticates to PET, but when PET calls SMART, SMART needs to trust the PET application itself. PET therefore uses a workload token from Cognito, which APIC validates. We are not authenticating the PET user twice; we are establishing service-to-service trust.”

If SMART later needs PET user identity, that becomes a delegated identity / token exchange / on-behalf-of design, which is more complex and is not required for the initial integration.

5. Why SMART UI Does Not Go Through APIC

“SMART UI is an internal browser application. The browser authenticates with Entra and calls the SMART API within the same application boundary. PET is a separate external system boundary, so it goes through APIC for gateway policy enforcement and workload token validation. We are not bypassing controls; we are applying the appropriate control at each boundary.”

6. TLS and Trust Boundaries

“TLS is enforced on every network leg. Termination and re-encryption may occur at trusted components. For SMART UI, browser-to-Nginx is HTTPS. For PET, encryption is preserved across the cNLB/APIC/SMART path, but not necessarily as one continuous TLS session.”

Do not claim exact PET TLS termination points unless the infra/APIC team has confirmed them.

7. Preventing PET from Bypassing APIC

“We use defense in depth. PET should have no direct network access to the SMART integration endpoint. Firewall and routing controls restrict that endpoint to APIC. APIC is the approved ingress and enforces authentication and policy. SMART also enforces application-level controls.”

If firewall or routing restrictions are not yet confirmed, present them as an explicit production dependency.

8. Traceability and Failure Handling

Correlation ID

“We use a correlation ID end-to-end for every PET transaction. PET passes it, APIC preserves it, and SMART logs and stores it with the request and response. That lets us trace one transaction across systems.”

If SQL Server is unavailable

“The application fails safely. No partial result is returned. We return a controlled error, log the correlation ID, generate alerting, and allow PET to handle retry according to the API contract.”

9. Idempotency

“SMART is analytical, not a high-risk transactional system. Most requests are calculation-oriented and do not create irreversible side effects, so idempotency is not a launch blocker. If we later persist scenarios more aggressively or automate retries, we will revisit duplicate-processing controls.”

Do not claim an idempotency key exists unless it is actually implemented.

10. Data Security and Access

“Data in transit is protected by TLS. Data at rest uses the bank-approved SQL Server encryption standard. Access is restricted using least privilege, with an AD service identity and SQL permissions. End users do not directly access the database.”

Store only what is needed for traceability and the business requirement. Do not equate “analytics” with “low sensitivity.”

11. Authorization Governance

“The business/application owner defines and approves access levels. Provisioning is performed through the bank’s identity governance process using AD or Entra groups, and SMART enforces those entitlements at runtime.”

For role changes or departures: removal from the relevant group means newly issued tokens no longer carry SMART entitlements, so access is denied.

12. Availability and DR

“SMART has DR at both application and database tiers across separate data centers. Recovery follows the enterprise failover process. The same versioned artifacts are promoted to primary and DR, configurations are version-controlled, environment-specific values and secrets are injected per environment, and automation is used where practical to prevent drift.”

If deployment automation is not fully implemented yet, call it the target state rather than implying it is already complete.

13. API Lifecycle and Change Management

“The API is contract-first using OpenAPI. We preserve backward compatibility by default. Breaking changes receive a new version, and migration is coordinated with PET through testing and release planning before the old version is retired.”

14. Capacity and Performance

“SMART is not a high-volume transactional system, but we size it based on expected concurrent users, PET request volume, and SQL workload. We will validate those assumptions with end-to-end performance testing before production.”

If asked for precise throughput/latency numbers and they are not yet baselined, say they are an open NFR being finalized. Do not invent numbers.

15. Data Retention and Classification

“We persist request and response data for traceability and business use. Retention and classification will align with enterprise data policy and be limited to what is necessary.”

16. Observability and Support

“SMART is monitored with APM and infrastructure alerts. Failures generate alerts with correlation IDs. The support team follows documented runbooks, and severity determines escalation.”

17. Architecture Rationale

“SMART remains on-prem to align with existing QAS data, SQL Server integration, and enterprise control requirements. PET remains in AWS and integrates through APIC using the bank-approved integration pattern. The architecture therefore preserves ownership boundaries while using standard enterprise controls at the integration point.”

18. Top Open Risks

“The main open risks are APIC and network readiness for the PET path, and production/DR operational maturity. Mitigation is to close delivery dependencies with the APIC and infrastructure teams, confirm network restrictions, and complete and test DR runbooks before production.”

19. Rapid-Fire Q&A

Q: Who issues the SMART UI token?

A: Microsoft Entra.

Q: Who validates the SMART UI token?

A: The SMART API.

Q: Who issues the PET token?

A: AWS Cognito.

Q: Who validates the PET token?

A: APIC, before forwarding to SMART.

Q: Does the React SPA contain a client secret?

A: No. It is a public client and uses Authorization Code Flow with PKCE through MSAL.

Q: 401 vs 403?

A: 401 means missing/invalid authentication. 403 means authenticated but not authorized.

Q: What prevents APIC bypass?

A: Network/routing/firewall restrictions plus application-level controls.

Q: How do you trace a failed PET request?

A: Correlation ID end-to-end across PET, APIC, SMART logs, and persisted request/response records.

Q: Biggest risks?

A: APIC/network readiness and prod/DR operational maturity.

20. Final 60-Second Rehearsal Script

“SMART has two entry points: browser UI and PET. For the UI, users authenticate with Entra through MSAL using Authorization Code Flow with PKCE; the SPA has no client secret. Traffic enters through Nginx, then React calls the SMART FastAPI backend, which validates the Entra access token and enforces authorization before accessing SQL Server.

For PET, PET uses a Cognito-issued workload token and reaches SMART only through the approved APIC path. APIC validates the token and applies policy before forwarding the request. Network restrictions should prevent direct bypass.

We use TLS in transit, bank-standard controls at rest, correlation IDs for end-to-end traceability, controlled failure behavior, contract-first OpenAPI versioning, monitoring and alerting, and DR across the app and database tiers. The main items to close before production are APIC/network readiness and DR operational maturity.”

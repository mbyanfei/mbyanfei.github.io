Podman deployment, service accounts & SELinux

A practical operating model for moving SMART away from personal rootless Podman storage toward a repeatable, service-account-owned deployment.

01 · CURRENT STATE

Why Jake cannot see your containers

Your Linux account

Your rootless Podman images, containers, networks and storage belong to your user namespace and storage.

Jake's Linux account

Jake gets a separate rootless Podman environment. He does not automatically see or manage the objects created under your account.

Key point: Don't solve this by making Podman's internal storage writable by multiple human users. Move the runtime ownership to one dedicated service identity.

The application server will still contain locally pulled image layers. But those should be treated as runtime cache/state—not the authoritative artifact. The registry becomes the place from which a known image version can be redeployed.

03 · INTERIM MIGRATION

No writable registry yet? Don't block.

Your read-only registry access means you need a temporary bridge. Export the existing image and load it into Podman while operating as the new service account.

# Current account
podman images
podman save -o smart-api.tar smart-api:TAG

# Transfer the tar through an approved server location,
# then operate as the SMART service account:
podman load -i smart-api.tar
podman images

Recreate the container from documented configuration/Quadlet. Do not try to copy Podman's internal container storage directory as your migration strategy.

04 · STORAGE

Where should the service account keep Podman storage?

Option A · Default home storage

Fine if the service account's home filesystem is local and has sufficient quota/capacity. Let Podman manage its own storage there.

Option B · Dedicated filesystem

Better when home quotas are small. Ask infra for a local path/filesystem and configure Podman's graphroot for the service account.

Do this before migration. If you already know the service-account home is capacity-constrained, establish the dedicated storage path first so you don't move all image layers twice.
05 · SELINUX

Think of security as two gates

Gate 1 · Unix permissions

Owner, group, other + rwx. This answers: does this user/process have normal filesystem permission?

+
Gate 2 · SELinux

Process and file security labels + policy. This answers: is this kind of process allowed to access this kind of object?

Both gates must allow the operation. That is why chmod 777 can still result in Permission denied.

06 · COMMANDS

Check SELinux and labels

# Is SELinux enforcing?
getenforce

# Normal Unix ownership/permissions
ls -ld /srv/smart

# SELinux context/label
ls -Zd /srv/smart

# Process SELinux contexts
ps -eZ

Enforcing

SELinux policy is active and violations can be blocked.

Permissive / Disabled

Permissive logs violations without blocking. Disabled means SELinux is not active.

07 · LABELS

What does an SELinux label look like?

system_u:object_r:container_file_t:s0
                  └───────┬───────┘
                       type

For day-to-day container troubleshooting, the type is usually the most useful piece. Podman bind mounts can request relabeling:

# Private to this container
podman run -v /srv/smart/data:/app/data:Z IMAGE

# :z is used when content is intentionally shared by multiple containers
Don't blindly relabel enterprise or shared system directories. For a dedicated SMART filesystem, agree on ownership, Podman storage configuration and SELinux context with infrastructure/security.

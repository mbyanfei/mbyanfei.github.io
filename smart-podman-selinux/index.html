SMART Podman Deployment & SELinux Notes

Context: SMART currently runs as rootless Podman containers under a personal Linux account. A shared service account is being provisioned so deployments are no longer tied to one developer.

1. Why Jake cannot see the current containers

Rootless Podman is user-scoped. Containers, images, networks, and storage created under one Linux user are normally not visible as that user's Podman objects to another user.

2. Recommended target model

Run SMART under the dedicated service account. Let Podman manage that account's local runtime storage, while treating the enterprise container registry as the long-term source of truth for versioned images. Keep deployment definitions in source control and use systemd/Quadlet for repeatable startup and lifecycle management.

3. Interim migration without a writable registry

# Current account
podman images
podman save -o smart-api.tar smart-api:TAG

# Service account
podman load -i smart-api.tar
podman images

Recreate the container from a documented Quadlet/container definition rather than copying the existing running container's internal Podman state.

4. Where should Podman storage live?

Default rootless storage under the service account is acceptable if its home filesystem has sufficient local capacity. If home quotas are small, ask infrastructure for a dedicated local filesystem/path and configure Podman's graphroot for the service account before migrating images.

Important: Do not simply make one Podman storage directory writable by multiple human accounts. Use one runtime identity—the service account—and controlled operational access around it.

6. SELinux in simple terms

Traditional Linux permissions are the first security gate: owner/group/other plus read/write/execute. SELinux is a second, independent security gate. A request must satisfy both.

Process → Unix permissions → SELinux policy → File/Directory
              Gate 1             Gate 2

7. Check whether SELinux is active

getenforce

Enforcing means policy blocks violations; Permissive logs but does not block; Disabled means SELinux is off.

8. What is an SELinux label?

Files/directories and processes have SELinux security contexts. Inspect a directory with:

ls -Zd /path/to/directory

A context may resemble system_u:object_r:container_file_t:s0. For container troubleshooting, the type portion such as container_file_t is especially important.

ps -eZ

9. Podman bind mounts and SELinux

For a private bind-mounted directory intended for one container, Podman commonly supports :Z:

podman run -v /srv/smart/data:/app/data:Z IMAGE

Lowercase :z is used when content needs to be shared among multiple containers. Do not blindly relabel enterprise/shared system directories.

10. Practical troubleshooting sequence

getenforce
ls -ld /srv/smart
ls -Zd /srv/smart
podman info
podman images
podman ps -a

If Unix ownership/permissions look correct but access still fails while SELinux is enforcing, inspect SELinux audit/AVC denials rather than disabling SELinux.

1

Understand the architecture first

The key idea is not “many AI agents.” It is parallel software work with isolation. Each session gets its own task context and can work in a separate Git worktree/branch.

One Git Repository main | +-----------------+-----------------+ | | | Session A Session B Session C | | | Worktree A Worktree B Worktree C Branch A Branch B Branch C | | | Agent A Agent B Agent C
Important: worktrees stop agents from overwriting the same working directory. They do not guarantee conflict-free merges.
2

Use a tiny practice repository

Do not start with production code. Create a deliberately boring Python project so you can focus on orchestration.

parallel-agent-lab/
├── app.py
├── calculator.py
├── README.md
└── tests/
    └── test_calculator.py
# calculator.py
def add(a, b):
    return a + b

def subtract(a, b):
    return a - b
3

Run exactly one agent first

Create a session and use a new working tree. Start in Interactive or Plan mode. Give the agent a sharply bounded task.

Add a multiply(a, b) function to calculator.py.
Add unit tests for it.
Do not modify unrelated files.
Run the tests after making the change and explain the diff.
4

Inspect what Git actually created

Open your normal repo terminal and inspect the worktrees. This makes the architecture concrete.

git worktree list
Same repository history | separate directory | separate branch | separate agent
5

Start Agent B before Agent A is finished

This reproduces the core pattern in the video. Give Agent B a genuinely independent task.

Improve README.md.
Document add(), subtract(), and multiply() with simple usage examples.
Do not change Python source code.
Repo | +-------+-------+ | | Agent A Agent B | | calculator.py README.md | | Worktree A Worktree B
Goal: learn to create independent workstreams instead of serially waiting for one AI task to finish before starting the next.
6

Add a reviewer/test agent

Parallel agents are more useful when they have different responsibilities, not when every agent is “write more code.”

Review the calculator project for missing tests and edge cases.
Do not change the implementation yet.
First give me a testing plan.
Agent A → implementation Agent B → documentation Agent C → testing / review
7

Practice context switching

Move between sessions without re-explaining the entire repository. Ask each session to summarize where it is and continue its own task.

What have you changed so far?
What remains?
What assumptions are you making?
8

Review instead of blindly accepting

The control loop matters more than the number of agents.

Prompt ↓ Plan ↓ Changed files ↓ Diff ↓ Tests ↓ Human review ↓ Merge
Rule: treat agent output as proposed engineering work, not as deterministic compiler output.
9

Deliberately create a conflict

You need to experience the failure mode, not just the happy path.

Agent D

Change subtract() so it validates inputs are numeric.

Agent E

Refactor subtract() to support Decimal inputs.
Lesson: parallel execution does not mean automatically composable execution. Conflicting semantics still need human reconciliation.
10

Learn task decomposition — the senior skill

Bad decomposition creates collisions. Good decomposition creates complementary evidence and implementation work.

Weak:

Agent 1 → redesign authentication Agent 2 → rewrite authentication Agent 3 → fix authentication

Better:

Agent 1 → analyze current auth architecture Agent 2 → write authentication tests Agent 3 → identify security risks Agent 4 → update auth documentation Then: Agent 5 → implement the agreed change
11

Use Git worktrees manually once

Do this once so the Copilot behavior stops feeling magical.

git checkout main
git worktree add ../feature-a -b feature-a
git worktree add ../feature-b -b feature-b

git worktree list

# cleanup later
git worktree remove ../feature-a
git worktree remove ../feature-b
12

Choose the right operating mode

Use more autonomy only as task boundaries become clearer.

Architecture / design → Plan New unfamiliar code → Interactive Well-scoped implementation → Autopilot
Recommendation: autonomy should increase with specification quality, not with confidence or impatience.
13

Graduate to a realistic Data/AI lab

Now use a project closer to real engineering work.

customer-analytics/
├── src/
│   ├── ingestion.py
│   ├── features.py
│   └── model.py
├── tests/
├── docs/
└── README.md
Agent 1 → Implement CSV → Parquet ingestion with Polars Agent 2 → Add data-quality tests: nulls, duplicates, schema, dates Agent 3 → Review features.py for data leakage; findings only Agent 4 → Write README architecture documentation
14

Mastery test

You understand the video when you can answer these without looking anything up:

2agents minimum for the first parallel lab
1intentional conflict to learn the failure mode
100%human review before integration
Final mental model: task decomposition → worktree isolation → context isolation → parallel execution → validation → dependency management → integration.

SMART & CT-Core Authentication — Study Guide

Purpose: clarify Entra ID, MSAL, OAuth2 Proxy, redirects, cookies/tokens, shared registrations, and runtime responsibility.

1. Two architectures

SMART: React SPA + MSAL → Microsoft Entra ID. The SPA obtains tokens and calls FastAPI. A BFF is optional, not required.

CT-Core shared platform: Nginx → per-app OAuth2 Proxy → per-app container. A clean Podman deployment is one proxy container paired with each application container.

2. SMART sequence — React + MSAL

1 User → Browser: open SMART URL
2 Browser → React SPA: load app
3 React/MSAL: no authenticated account/token
4 MSAL → Browser → Entra: authorize request (client_id, redirect_uri, PKCE, scopes)
5 Entra → User: authenticate / SSO / MFA as policy requires
6 Entra → Browser: authorization response to registered redirect URI
7 MSAL: completes code + PKCE flow and obtains tokens
8 React → SMART FastAPI: API request + Authorization: Bearer <access_token>
9 API/gateway: validate token as designed; app performs authorization
10 FastAPI → React → User: response rendered

Key: with a pure SPA, the app normally relies on OAuth tokens rather than an app-created backend session cookie.
The MSAL configuration chooses the redirect URI; it can be the app root or a dedicated route.

3. CT-Core sequence — OAuth2 Proxy

1 User → app3.ctcore...: request App 3
2 Nginx → App 3 OAuth2 Proxy: route request
3 Proxy: no valid session cookie
4 Proxy → Browser → Entra: authorize request using shared/per-app client_id + App 3 redirect_uri
5 Entra: verify client_id and exact redirect URI is registered
6 Entra → User: authenticate / SSO / MFA
7 Entra → Browser → App 3 callback: authorization response
8 App 3 OAuth2 Proxy: complete OAuth/OIDC flow
9 Proxy → Browser: Set-Cookie (secure session cookie)
10 Browser → Proxy: subsequent request + cookie
11 Proxy: validate session; optionally enforce configured identity constraints
12 Proxy → App 3 container: authenticated request
13 App 3: enforce application authorization/business rules
14 App 3 → Proxy → Nginx → Browser: response

4. One shared Entra registration: technically feasible

One CT-Core registration can contain multiple redirect URIs. Multiple OAuth2 Proxy instances can use the same client ID while each supplies its own registered callback URI. It can also define multiple app roles. Tokens may contain roles assigned to the user/service principal; each application must enforce the roles relevant to it.

But: this creates one shared identity/security and lifecycle boundary. A bad redirect/configuration or broad permission change can affect multiple apps. For critical or independently owned apps, separate registrations are cleaner. Keeping SMART separate is therefore sensible.

5. Redirect URI / callback URL

Redirect URI is the OAuth/OIDC term. Callback URL is common informal language for essentially the same endpoint in this context. OAuth2 Proxy commonly uses a dedicated callback path such as /oauth2/callback. MSAL React has no universal callback path: the configured redirect URI controls it.

URI is the broader identifier concept; URL is a type of URI. In Entra discussions, say redirect URI.

6. Cookies vs tokens

Cookies are stored by the browser. A server/proxy can create the session state and return a Set-Cookie header; the browser stores the cookie and sends it on later requests. OAuth2 Proxy typically works this way. A pure MSAL SPA instead obtains OAuth/OIDC tokens in the browser. A BFF moves token handling to the backend and gives the browser a session cookie.

7. Podman configuration pattern

Nginx
 ├─ app2 hostname → oauth2-proxy-app2 container → app2 container
 ├─ app3 hostname → oauth2-proxy-app3 container → app3 container
 └─ app4 hostname → oauth2-proxy-app4 container → app4 container

Keep the OAuth2 Proxy image generic.
Inject per-app configuration at container start using environment variables,
mounted config files, and an approved secret-management mechanism.
Typical settings: client ID, redirect URI, issuer, upstream URL, cookie settings,
allowed groups/claims, and secret references.

8. Entra vs SailPoint vs CyberArk

Entra ID: identity provider/authentication and token issuance. SailPoint: identity governance—access request, approval, provisioning/deprovisioning and lifecycle governance; normally not in the live HTTP login path. CyberArk: privileged credential/secrets management. These solve different problems.

9. Critical distinction: authentication vs authorization

OAuth2 Proxy can establish that a user has authenticated, but that does not automatically make every authenticated user authorized for every hosted app. Groups/app roles/claims and enforcement must be designed deliberately. Treat “who are you?” and “are you allowed into/do this in App 3?” as separate controls.

10. Questions for M365 Engineering / developer

  1. For SMART, what exact MSAL redirectUri will be configured?
  2. For CT-Core, what exact OAuth2 Proxy callback path and hostname convention will each app use?
  3. Will CT-Core intentionally use one shared Entra client ID, or separate registrations as apps mature?
  4. If shared, how are app roles/groups mapped and enforced per app?
  5. Where are client credentials/cookie secrets stored and injected?
  6. Are cookies Secure, HttpOnly and appropriately SameSite-scoped?
  7. Who owns changes to shared redirect URIs, roles and permissions?

SMART & CT-Core Authentication — Study Guide

Entra ID • MSAL • OAuth2 Proxy • Redirect URIs • Cookies vs Tokens • Podman/Nginx shared platform

1. Two architectures

SMART: React SPA + MSAL → Microsoft Entra ID. The SPA initiates sign-in, obtains tokens, and calls FastAPI. A BFF is optional.

CT-Core shared platform: Nginx → per-app OAuth2 Proxy → per-app container. A clean Podman deployment is one proxy container paired with each application container.

2. SMART — swim-lane sequence diagram (React + MSAL)

This is the detailed runtime flow from opening SMART through Entra authentication, token acquisition, API invocation, and response rendering.

sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant R as SMART React SPA
    participant M as MSAL Browser
    participant E as Microsoft Entra ID
    participant G as NGINX API Gateway
    participant F as SMART FastAPI

    U->>B: Open SMART URL
    B->>R: Load React application
    R->>M: Check authenticated account and cached token

    alt No authenticated account or usable token
        R->>M: Start sign in flow
        M->>E: Authorization request with client ID, redirect URI, scopes, and PKCE
        E-->>U: Request authentication, SSO, or MFA
        U-->>E: Complete authentication
        E-->>B: Redirect to registered SMART redirect URI with authorization code
        B-->>M: Deliver authorization response
        M->>E: Exchange authorization code and PKCE verifier for tokens
        E-->>M: Return ID token and access token
        M->>M: Cache account and tokens
    else Valid account and access token already exist
        M->>M: Reuse cached account and token
    end

    M-->>R: Return SMART API access token
    U->>R: Run scenario
    R->>G: API request with bearer access token
    G->>F: Forward API request
    F->>F: Validate token claims and enforce authorization
    F-->>G: Return API response
    G-->>R: Return API response
    R-->>B: Render result
    B-->>U: Display SMART response

    Note over R,M: MSAL orchestrates the browser OAuth and OIDC flow
    Note over E: Entra ID authenticates the user and issues tokens
    Note over G,F: Gateway validation does not replace application authorization

3. CT-Core — swim-lane sequence diagram (OAuth2 Proxy)

This shows one application on the shared CT-Core platform: Browser → Nginx → that app's OAuth2 Proxy → Entra ID → application container.

sequenceDiagram
    autonumber
    actor U as User
    participant B as Browser
    participant N as NGINX
    participant P as OAuth2 Proxy
    participant E as Microsoft Entra ID
    participant A as App Container

    U->>B: Open App 3 URL
    B->>N: HTTPS request for App 3
    N->>P: Route request to App 3 OAuth2 Proxy
    P->>P: Check session cookie

    alt No valid session
        P-->>B: Redirect browser to Entra authorize endpoint
        B->>E: Authorization request with client ID, redirect URI, scopes, and state
        E-->>U: Request authentication, SSO, or MFA
        U-->>E: Complete authentication
        E-->>B: Redirect to App 3 callback with authorization code
        B->>N: Request App 3 OAuth2 callback
        N->>P: Route callback to App 3 proxy
        P->>E: Exchange authorization code for tokens
        E-->>P: Return tokens and claims
        P-->>B: Set secure session cookie and redirect to original URL
        B->>N: Repeat original request with session cookie
        N->>P: Route request
    else Valid session exists
        P->>P: Validate existing session cookie
    end

    P->>A: Forward authenticated request upstream
    A->>A: Enforce app authorization and business rules
    A-->>P: Return application response
    P-->>N: Return response
    N-->>B: Return HTTPS response
    B-->>U: Render App 3

    Note over P,E: OAuth2 Proxy orchestrates OIDC and Entra performs authentication
    Note over P: Proxy creates the session cookie and browser stores it
    Note over A: Authentication does not replace application authorization

Key point: OAuth2 Proxy orchestrates the sign-in flow and creates the application session cookie. Entra ID authenticates the user. The application still owns application-specific authorization.

4. Shared Entra registration — technically feasible

One CT-Core registration can contain multiple redirect URIs. Multiple OAuth2 Proxy instances can use the same client ID while each supplies its own registered callback URI. The registration can also define multiple app roles.

Trade-off: this creates one shared identity and lifecycle boundary. That reduces registration friction, but increases coupling and blast radius. Keeping SMART on its own registration is the cleaner boundary for a more critical application.

5. Redirect URI / callback URL

Redirect URI is the formal OAuth/OIDC term. Callback URL is common informal language for essentially the same endpoint in this context.

OAuth2 Proxy commonly uses a dedicated path such as /oauth2/callback. MSAL React has no universal callback path: Jake's MSAL configuration determines the exact redirect URI, which could be the application root or a dedicated route.

6. Cookies vs tokens

Cookies are stored by the browser. A server or proxy can create the session and return a Set-Cookie header; the browser then stores and resends the cookie. OAuth2 Proxy commonly works this way.

A pure MSAL SPA usually relies on OAuth/OIDC tokens in the browser. A BFF moves token handling to the backend and exposes only a session cookie to the browser.

7. Podman pattern

Nginx
 ├─ app2 hostname → oauth2-proxy-app2 container → app2 container
 ├─ app3 hostname → oauth2-proxy-app3 container → app3 container
 └─ app4 hostname → oauth2-proxy-app4 container → app4 container

Keep the OAuth2 Proxy image generic. Inject per-app configuration at container start via environment variables, mounted config files, and an approved secret-management mechanism.

8. Entra vs SailPoint vs CyberArk

Entra ID: identity provider, authentication, token issuance.

SailPoint: identity governance — access requests, approvals, provisioning/deprovisioning, recertification and lifecycle governance. It normally does not sit in the live HTTP login path.

CyberArk: privileged credential / secrets management.

9. Authentication vs authorization

OAuth2 Proxy can establish that a user has authenticated, but that does not automatically authorize that user for every hosted application. Groups, app roles, claims and enforcement must be designed deliberately.

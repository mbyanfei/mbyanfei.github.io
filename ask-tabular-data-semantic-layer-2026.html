Enterprise Conversational Analytics • 2026

Ask Questions About Enterprise Tabular Data

How natural-language analytics, semantic layers, context layers, ontologies, and agentic text-to-SQL are converging — and what architecture is appropriate when users expect trustworthy answers about sales, finance, deposits, NII, revenue, forecasts, or other governed metrics.

Core conclusion: “Can an LLM generate SQL?” is no longer the hard question. The hard question is whether the system can reliably understand the intended business definition, grain, joins, time logic, security, and approved calculation — and know when not to answer.

1. Where the technology is now

Text-to-SQL capability has improved dramatically. Enterprise-focused benchmarks such as Spider 2.0 and BIRD show rapid gains, especially when systems use schema retrieval, tools, query repair, examples, and multi-step planning. But benchmark success does not remove the enterprise semantics problem.

2. Why raw text-to-SQL is dangerous

A question like “What was commercial deposit growth last quarter?” hides critical decisions: what counts as commercial, average versus ending balance, gross versus net-of-sweeps, fiscal versus calendar quarter, effective versus posting date, legal entity, FX treatment, customer hierarchy, and denominator logic.

Syntax correctness ≠ analytical correctness. A system can produce valid SQL and still return a plausible but materially wrong number.

3. Is a semantic layer required?

Experiment

Optional Raw NL→SQL can be acceptable for prototypes and analyst exploration.

Enterprise self-service

Strongly recommended Governed metrics, joins, dimensions and definitions materially reduce ambiguity.

Finance / risk / regulatory

Treat as mandatory Business definitions should be executable and traceable rather than invented by the model.

7. Warehouse-native semantics

Snowflake

Semantic Views define logical tables, facts, dimensions, metrics, relationships, synonyms and descriptions. Cortex analytics/agent experiences can combine those models with verified queries and custom instructions.

Databricks

Metric Views standardize dimensions and measures in Unity Catalog. Genie-style agents add instructions, example SQL, trusted assets, benchmark sets and domain context.

8. Ontology is not the same as a metrics layer

Semantic metric layer
= HOW DO WE CALCULATE THINGS?

Ontology
= WHAT THINGS EXIST AND HOW ARE THEY RELATED?

A metric layer can define Revenue, Average Balance, NIM, Product and Region. An ontology can represent Customer → Account → Product, Customer → Relationship Manager, Transaction → Account, and relationships spanning deposits, loans, CRM and service cases.

9. The emerging context layer

Modern systems increasingly separate data semantics from analytical and user context.

Data semantics

Tables, columns, joins, grain, metrics, aggregation rules.

Analytical context

Business rules, default filters, exclusions, approved procedures, terminology, examples.

User context

Role, region, entitlements, conversational state and relevant preferences.

10. A catalog is not a semantic layer

Catalogs such as Purview, Collibra, Alation, Atlan and Unity Catalog can describe tables, columns, owners, lineage, quality and classifications. That is valuable grounding, but it is not necessarily an executable definition of Revenue, NII, Average Balance, Churn or Liquidity Utilization.

For “What was NII last month?”, use a certified metric. For “Which 20 customers had unusually large wire transfers versus their prior 90-day behavior?”, agentic SQL or an analytical workflow may be more appropriate.

13. Three answer classes

Certified

Entirely derived from governed semantic metrics, with metric identity, source model, time period and filters visible.

Exploratory

Generated through AI/SQL against approved data assets, with query lineage and reviewability.

Unable to determine

When the term is ambiguous or no approved definition exists, clarify rather than fabricate.

14. Build a golden-question benchmark

Before releasing an “Ask Finance” or “Ask Data” capability, collect 100–300 real questions and store the expected interpretation, metric, dimensions, filters, expected SQL/DAX or semantic query, expected result, and tolerance.

17. Bottom line

Do not design an “NL-to-SQL system.” Build a “business question → governed answer system.”

SQL should be one execution mechanism underneath the platform, not the architecture itself.

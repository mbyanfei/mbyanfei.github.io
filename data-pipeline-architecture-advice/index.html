Solution Architecture Review

Luke — How I Would Reset This Data Pipeline

Architecture guidance for simplifying the pipeline, restoring data observability, and moving from a code-heavy implementation back to a data-first engineering model.
Prepared as follow-up to our working session • September 2026

Luke, you asked me to look at the situation because the pipeline has become difficult to debug, difficult to validate, and increasingly dependent on a large body of Python that you do not fully trust. My recommendation is not to keep refactoring that code indefinitely. I would reset the design around the data and the business logic.

The principle I want you to work from:
This is primarily a data pipeline, not an application. Focus first on the source data, business transformation rules, intermediate results, and validation. Use application code only where it adds something the database and SQL cannot provide.

1. What I Think Went Wrong

The current pipeline did not become messy because Python is inherently wrong. It became messy because too many responsibilities were pushed into Python at once: extraction, transformation, business logic, intermediate-state handling, debugging, logging, QA, file management, and orchestration. AI then accelerated code generation faster than the team established a clear data model and validation model.

Data logic is buriedBusiness rules are spread across functions instead of being visible as clear transformation steps.
Intermediate states are hard to inspectYou often have to run the pipeline and then investigate through logs or generated diagnostics.
AI increased volume, not clarityGenerated code can be syntactically good while still producing a system nobody can reason about end to end.

Austin's point about cyclomatic complexity is valid, but I want to clarify the term. Cyclomatic complexity is not the number of times a function is invoked. It is roughly a measure of the number of independent execution paths through the code — branches, loops, conditions, exception paths, and so on. Large functions with many paths are harder to test and maintain.

Reducing cyclomatic complexity is useful, but it is not the root fix here. You can split a 1,788-line pipeline into many smaller functions and still have a system whose data behavior is opaque.

2. Separate Three Different Problems

I would stop treating every failure as a Python debugging problem. There are really three different layers:

LayerQuestionPrimary Tool
DataIs the source data complete, valid, and what we think it is?SQL profiling and source queries
TransformationDid our joins, filters, attribution rules, aggregations, and business rules produce the right result?SQL / CTEs / data tests
OrchestrationDid the steps execute in the right order, for the right period, with logging and failure handling?Thin Python + scheduler

Your current implementation mixes these layers heavily. That makes a responder-count issue look like a software-debugging exercise when it may simply be a join, filter, date-window, mapping, null, or source-data problem.

3. Push the Heavy Transformation Back to IDP / Netezza

Your sources are already in IDP, and you can write results back to IDP. That matters. You have a database platform designed to process large data sets using set-based operations and parallel execution. I would use it.

Python │ │ execute SQL ▼ IDP / Netezza │ ├── joins ├── filters ├── business rules ├── aggregation └── INSERT / CREATE TABLE │ ▼ Output table

Avoid pulling millions of rows into Python simply so Polars or Pandas can reproduce operations the database already performs well. That creates unnecessary memory pressure, chunking logic, serialization, file handling, and write-back complexity.

Important technical correction: pyodbc still uses a database cursor internally. The issue is not “cursor versus no cursor.” The real distinction is set-based SQL versus row-by-row processing. Let Python submit SQL statements; let the database process the data as sets.

5. Build Observability into the Data Flow

The missing capability is not another HTML diagnostic report. The missing capability is the ability to inspect the data at every meaningful transformation boundary.

SELECT COUNT(*) FROM targeted_customers;

SELECT COUNT(*) FROM candidate_responses;

SELECT *
FROM attributed_responses
WHERE campaign_id = 'XYZ';

SELECT campaign_id,
       COUNT(*) AS targeted,
       SUM(responder_flag) AS responders
FROM final
GROUP BY campaign_id;

When the business says, “This campaign has zero responders and that does not look right,” debug backward through the data:

Final responder count = 0 │ ▼ Did attribution produce responders? │ ▼ Were candidate responses found? │ ▼ Was the target product mapped correctly? │ ▼ Were the right customers targeted? │ ▼ Was the campaign loaded correctly? │ ▼ Source data

That is the debugging model I want you to develop. You are debugging the data lineage and transformation, not blindly traversing Python functions.

6. A Giant CTE Is a Starting Point, Not the Final Architecture

I suggested using a large CTE because it gives you visibility and lets you reconstruct the logic quickly. I would not leave the entire production system as one enormous SQL statement.

staging ├── stg_campaign ├── stg_email └── stg_customer_product intermediate ├── int_campaign_targets ├── int_email_delivery ├── int_response_candidates └── int_response_attribution output / marts ├── email_channel ├── dm_channel └── campaign_view

This is also why I mentioned dbt. The value of dbt is not that we need another fashionable framework. The value is that it formalizes a SQL-first architecture around models, dependencies, tests, documentation, lineage, and materialization. If dbt is practical in your environment, evaluate it. If it is not, we can implement the same core discipline using SQL files and a thin Python runner.

7. Do Not Rewrite the Whole Pipeline at Once

The existing Python pipeline may be messy, but it is valuable as a reference implementation. Use it to validate the replacement.

Existing Python result │ ├──────── compare ────────┐ │ │ ▼ ▼ row counts New SQL result distinct customers campaign counts responder counts null rates duplicate rates aggregates record-level differences

When the SQL version reproduces the correct behavior — or exposes where the old behavior was wrong — retire that portion of the Python transformation. Then move to the next output. That is safer than another large rewrite.

8. Test the Data, Not Just the Python

Unit tests matter when you have real reusable Python logic. But many of the problems you described are not conventional software-unit-test problems. They are data-quality and business-rule problems.

-- Key uniqueness
SELECT campaign_id, customer_id, COUNT(*)
FROM email_channel
GROUP BY campaign_id, customer_id
HAVING COUNT(*) > 1;

-- Required field
SELECT COUNT(*)
FROM email_channel
WHERE customer_id IS NULL;

-- Reconciliation
SELECT campaign_id,
       COUNT(*) AS targets,
       SUM(responder_flag) AS responders
FROM email_channel
GROUP BY campaign_id;

Also build assertions around expected ranges: record-count changes, null-rate thresholds, responder-rate changes, referential integrity, accepted-value rules, and known campaign examples supplied by the business.

9. How I Want You to Use AI

I am not suggesting that you stop using GitHub Copilot or other LLM tools. I am suggesting that you change the order of operations.

Bad sequenceAsk AI to build the pipeline → code grows → discover incorrect data → ask AI to explain its own generated code.
Better sequenceUnderstand requirement → inspect source data → validate transformation in SQL → then use AI to automate or refactor.
Best use of AI hereGenerate boilerplate, test ideas, SQL drafts, documentation, comparisons, orchestration code, and refactoring suggestions — with you retaining the mental model.
AI can help write the pipeline. It should not become the only entity that understands the pipeline.

10. Target Architecture

IDP / NETEZZA │ source tables │ ▼ SQL models │ ┌────────────┼────────────┐ ▼ ▼ ▼ staging intermediate output │ │ │ └────────────┼────────────┘ │ data-quality tests │ ▼ production tables ORCHESTRATION LAYER ┌────────────────────────────┐ │ thin Python runner │ │ │ │ connect │ │ execute SQL models │ │ record run_id / dates │ │ run validation │ │ log status │ │ fail or succeed clearly │ └────────────────────────────┘ │ ▼ scheduler / enterprise orchestration

The Python runner should be boring. That is a feature. Most of the intelligence should be visible in the SQL models and data-quality rules.

11. What I Would Do Next

  1. Choose one representative table — preferably one with a known defect such as the responder issue.
  2. Document the business rule in plain English before changing code.
  3. Identify every source table and verify the supplied queries independently in a SQL IDE.
  4. Reconstruct the transformation in SQL using CTEs and a small, representative date range.
  5. Validate each intermediate step with counts, samples, null checks, and known business cases.
  6. Get business confirmation on the resulting output before automating it.
  7. Wrap the validated SQL with thin Python only for parameters, execution, logging, and orchestration.
  8. Compare against the existing pipeline and investigate every material difference.
  9. Retire the corresponding old Python transformation only after the replacement is proven.
  10. Repeat one business process at a time.

12. Tooling

DBeaver versus VS Code is not the architectural decision. DBeaver is simply a better environment for spending hours exploring tables, writing SQL, comparing result sets, and inspecting schemas. If SQL becomes your primary development surface for this work, I would use a proper SQL IDE.

Scheduling also comes later. Cron, an enterprise scheduler, Prefect, or another orchestrator can all work. Do not spend much effort optimizing the scheduler while you still do not trust the data pipeline itself.

My Bottom Line

Luke, I do not think your main problem is that the current Python needs another round of cleanup. The bigger problem is that the implementation grew faster than the team's understanding of the data flow.

Go back to fundamentals: understand the business requirement, understand the source data, express the transformation clearly, inspect every meaningful intermediate state, validate the output, and only then automate it.

For a data pipeline, optimize first for correctness, transparency, lineage, and debuggability. Optimize the code only after those are under control.

If you rebuild one use case this way, I think you will immediately see whether this approach is materially easier to understand and maintain. If it is, use that pattern as the template for the rest of the pipeline.

Architecture note: the recommended pattern assumes the transformations can be executed efficiently in IDP/Netezza and that the team has appropriate read/write permissions. Specialized transformations that genuinely require Python can remain in Python, but they should be isolated and have explicit input/output contracts.

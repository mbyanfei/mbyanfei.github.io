Foundation API Lifecycle & Architecture Big-picture thinking before diving technical
F1 Walk me through the full lifecycle of an API you built — from the initial design conversation all the way to it running in production and being maintained. +
Expected Answer

A strong candidate describes a structured lifecycle, not just "I wrote some code and deployed it." Phases they should cover:

  • Requirements & contract design — working with stakeholders to define what the API needs to do, who will consume it, and what the data contract looks like. Often produces an OpenAPI spec as the design artifact before any code is written.
  • API design — deciding on resource naming, endpoint structure, versioning strategy, authentication model. Good engineers do this on paper first.
  • Implementation — writing code with proper validation, error handling, logging, and tests. Not just the happy path.
  • Documentation — generating or writing API docs (Swagger UI, Redoc, Postman collections) so consumers can self-serve.
  • Deployment & CI/CD — containerizing (Docker), deployment config (Kubernetes, ECS, Lambda), CI pipelines that run tests on every PR.
  • Observability — monitoring (latency, error rates, request volume), alerting, and log aggregation.
  • Versioning & deprecation — managing API evolution without breaking consumers over time.
✓ Walks through all phases naturally with concrete examples. Treats API design as a design activity, not just a coding one.
✗ Jumps straight to "I coded the endpoints" — skips design, documentation, and observability. Signals someone who writes scripts, not maintains systems.

› "You mentioned the design phase — what does that actually look like before any code is written? What artifacts come out of it?" +
Expected Answer

The main artifact is an OpenAPI (formerly Swagger) spec — a structured document (YAML or JSON) that defines every endpoint, its inputs, outputs, and error responses. This becomes a contract between the API team and consumers before a single line of code is written.

Other design artifacts include: an API design document covering versioning strategy, auth model, and naming conventions; a data model diagram showing the resources and their relationships; and often a sequence diagram for complex flows (e.g., OAuth handshake, async job pattern). Strong candidates may also mention running the spec through a mock server so consumers can start building against it immediately.

A red flag: "I just started coding and documented it afterward" — this usually produces poorly designed APIs that are hard to evolve.

› "How do you know when the API is ready to ship — what does your definition of done look like?" +
Expected Answer

A strong definition of done covers: all endpoints implemented and tested (including error paths), integration tests passing in CI, documentation published and reviewed by at least one consumer, security review completed (auth, input validation, no secrets in logs), monitoring and alerting configured, and a rollback plan documented.

Bonus: they mention a staging environment smoke test — running a real end-to-end call against staging before any production deploy. Or a load test to verify the API handles expected peak traffic before launch.

A weak answer: "when the code works" — no mention of observability, docs, or consumer readiness.

› "What happens to the API six months after launch? Who owns it, and how do you handle change requests from consumers?" +
Expected Answer

Strong candidates treat post-launch maintenance as a normal, expected part of ownership — not an afterthought. Key practices: a designated owner or team responsible for on-call, monitoring dashboards, and SLAs; a process for handling consumer change requests (feature requests go through a backlog, bug reports go through an issue tracker); and a clear policy for what counts as a breaking vs non-breaking change.

Non-breaking changes (additive) can be deployed without versioning — e.g., adding a new optional field. Breaking changes (removing a field, changing a type, changing behavior) require a version bump and deprecation timeline communicated to all consumers.

A weak answer: "I hand it off to another team and move on." Someone who has truly owned a production API understands that long-term maintenance is where most of the real work lives.

F2 What components typically sit in front of or around a production API — beyond just the application code itself? +
Expected Answer

A production API is never just a Python process. Key components:

  • API Gateway — sits in front of all APIs, handles routing, rate limiting, auth enforcement, SSL termination. Examples: AWS API Gateway, Kong, NGINX, Apigee.
  • Load Balancer — distributes traffic across multiple instances. Enables horizontal scaling and zero-downtime deployments.
  • Cache layer — Redis or Memcached for frequently-requested, expensive-to-compute responses.
  • Message queue — Kafka, SQS, RabbitMQ for async work handed off from the API.
  • Database layer — with connection pooling (PgBouncer) to prevent exhausting DB connections under load.
  • Observability stack — logging (CloudWatch, Datadog, ELK), metrics (Prometheus/Grafana), distributed tracing (Jaeger, X-Ray).
  • Secret management — AWS Secrets Manager, Vault — never hardcoded credentials.
✓ Describes the API as one component in a larger system. Mentions API Gateway and understands why offloading cross-cutting concerns matters.
✗ Only thinks about the app code — no awareness of surrounding infrastructure. Likely has never deployed to a real cloud environment.

› "What specific things would you configure at the API Gateway vs keeping in the application code? Why?" +
Expected Answer

At the API Gateway: rate limiting, IP allowlisting/blocklisting, SSL/TLS termination, request/response logging at the edge, basic API key validation, routing to different backend services, CORS headers, and DDoS protection. These are cross-cutting concerns — they apply to every API in the organization and don't belong in individual application code.

In the application code: business logic, fine-grained authorization (which user can see which record), request body validation, domain-specific error handling, and anything that requires database context. The rule of thumb: if the logic requires knowing what the request contains, it belongs in the app. If it applies regardless of content, consider the gateway.

A strong candidate understands this boundary clearly and has made these decisions on real systems.

› "If your API suddenly gets 10x the normal traffic, what in this architecture absorbs that, and what breaks first?" +
Expected Answer

The load balancer and API Gateway typically handle the traffic surge gracefully — they're designed to scale horizontally. The API application instances can also scale horizontally (auto-scaling groups, Kubernetes HPA) with a short lag.

The component most likely to break first is the database — specifically the connection pool. Each API instance holds a pool of DB connections, and 10x instances means 10x connections. If the DB has a connection limit (Postgres default is 100), it gets exhausted quickly. This is why PgBouncer or RDS Proxy are essential in production — they multiplex many application connections into a smaller number of real DB connections.

After the DB, the cache layer (Redis) could become a bottleneck if it's a single node and all cache misses suddenly hit the DB. A well-designed system adds cache replicas and uses read-through caching to absorb this.

› "How do you manage secrets like DB passwords and API keys across different environments?" +
Expected Answer

The cardinal rule: secrets never go in source code, config files, or environment variable files that get committed. Common production approaches:

  • AWS Secrets Manager / Parameter Store — secrets are stored encrypted in AWS, fetched by the application at startup or request time using IAM roles. No secrets in code or deployment scripts.
  • HashiCorp Vault — dedicated secrets management platform, supports dynamic credentials (short-lived DB passwords generated on demand).
  • Kubernetes Secrets — base64-encoded secrets injected as environment variables into pods (though this is considered weaker without additional encryption at rest).

Per environment (dev/staging/prod), separate secret stores or namespaces are used. Developers should never have access to production secrets. Rotation policies should be automated. A strong candidate mentions secret rotation and access auditing as part of the practice.

F3 How do you approach API documentation — who writes it, when, and what tools do you use? +

› "If a developer from another team needs to integrate with your API, what do you hand them and what does onboarding look like?" +
Expected Answer

A well-run API onboarding delivers: a link to the live Swagger UI or Redoc documentation where they can read all endpoints and try them interactively; a Postman or Insomnia collection they can import and run immediately; sandbox/staging credentials so they can test without touching production data; and a getting-started guide covering auth setup, base URL, and the first working request.

Strong candidates also mention a developer experience review — where a member of the consuming team is walked through the API by the builder before it goes live, to catch confusing design decisions early. The goal is that a developer should be able to make their first successful API call within 15–30 minutes of receiving documentation.

› "Have you had a situation where your documentation was wrong or out of date and a consumer built against it incorrectly?" +
Expected Answer

Honest candidates who have shipped real APIs will have a story here. The key is what they learned: the root cause is almost always docs that are written separately from code and allowed to drift. The fix is documentation that is generated from code (auto-generated OpenAPI spec) or tightly coupled to code via tests — so when the code changes, the docs either update automatically or the CI pipeline fails.

A strong candidate mentions contract testing as a preventive measure: the consuming team's tests run against the API spec, and if the spec changes in a breaking way, their tests catch it before deployment. Tools like Pact or schemathesis enable this.

› "What's the difference between documentation for internal developers vs external API consumers?" +
Expected Answer

Internal documentation can assume shared context — it can reference internal systems, use org-specific terminology, and assume the reader knows the general architecture. It focuses on implementation details: where the code lives, how to run it locally, deployment procedures, and architecture decisions.

External documentation must assume zero context. It needs: a clear description of what the API does and why someone would use it; complete auth setup instructions from scratch; working code examples in multiple languages; error code reference; rate limit details; SLA commitments; and a support/contact path. The bar is much higher because external consumers can't just ask a colleague.

A strong candidate may mention the concept of a developer portal (like Stripe's or Twilio's docs) as the gold standard for external API documentation.

F4 How do you think about API security at a high level — not just authentication, but the broader threat surface? +
Expected Answer

Authentication is the entry-level answer. A production API engineer thinks in layers:

  • Input validation — validate all inputs with Pydantic. Reject oversized payloads. Prevents injection attacks.
  • Transport security — TLS/HTTPS everywhere, never HTTP in production.
  • OWASP API Security Top 10 — key items: Broken Object Level Authorization (BOLA), Excessive Data Exposure, Security Misconfiguration, Mass Assignment.
  • Rate limiting & DDoS protection — preventing abuse even from authenticated users.
  • Dependency security — scanning Python packages for CVEs (pip-audit, Dependabot).
  • Principle of least privilege — each service only has the permissions it needs.
  • Audit logging — logging who did what to sensitive resources.
✓ Mentions OWASP or BOLA — a very common real-world vulnerability that data engineers don't typically consider.
✗ Security = "just add authentication." No awareness of object-level authorization, input validation, or common API attack patterns.

› "What's Broken Object Level Authorization — can you give me a concrete example of how it happens?" +
Expected Answer

BOLA (also called IDOR — Insecure Direct Object Reference) is the most common API vulnerability. It happens when an API uses predictable IDs to access objects without verifying the requesting user owns that object.

Example: A user logs in and sees their order at GET /orders/1042. They change the URL to GET /orders/1043 — and get someone else's order, because the API only checks "is the user authenticated?" but not "does this user own order 1043?"

The fix: every object access must include an ownership check. In code: after fetching the order from the DB, verify order.user_id == current_user.id before returning it. If not, return 404 (not 403 — returning 403 confirms the object exists, which is an information leak). This check must happen in every endpoint, not just some.

› "Say your API endpoint returns a user profile. What security checks happen before that data is returned?" +
Expected Answer

A complete sequence of checks: (1) Authentication — is there a valid token in the request header? If not, return 401. (2) Token validation — is the JWT signature valid, not expired, and issued by the correct issuer? (3) Object-level authorization — is the requesting user the owner of this profile, or do they have an admin role that permits viewing others' profiles? If not, return 404. (4) Field-level filtering — strip any sensitive fields from the response that the caller shouldn't see (e.g., hashed password, internal flags, payment details). Only return what this caller is authorized to see. (5) Rate limiting check — has this client exceeded their allowed request rate?

A weak answer stops at step 1. A strong answer covers all five and ideally mentions that these checks should be enforced in a centralized dependency, not copy-pasted into each endpoint.

› "If a security audit flagged your API, what are the three most common things you'd expect to see?" +
Expected Answer

The three most common findings in real API security audits:

  • BOLA / IDOR — missing object-level ownership checks. Incredibly common even in mature systems because it requires a check on every single data access, not just the endpoint entry point.
  • Excessive data exposure — endpoints returning full database objects (all fields) when the consumer only needs a subset. Sensitive fields get leaked unintentionally. Fix: use response schemas that explicitly define what fields are returned, rather than serializing entire ORM objects.
  • Missing rate limiting or no throttling on sensitive endpoints — login endpoints with no brute-force protection, password reset endpoints that can be hammered, or data export endpoints with no volume limits.

Bonus findings they might mention: JWT algorithm confusion attacks (accepting "none" as a valid algorithm), verbose error messages leaking stack traces, or hardcoded credentials found in source history.

F5 How do you monitor a production API — what metrics do you track, and how do you know something is wrong before users complain? +
Expected Answer

Observability has three pillars:

  • Metrics — the "four golden signals": Latency, Traffic (req/sec), Errors (error rate), Saturation (CPU/memory). Track p95 and p99 latency — not averages.
  • Logs — structured JSON logs capturing: timestamp, request ID, endpoint, status code, response time, user ID. Tools: CloudWatch, Datadog, ELK.
  • Distributed tracing — tracks a request across multiple services. Tools: AWS X-Ray, Jaeger, OpenTelemetry.

Alerting triggers: error rate spike above threshold, p95 latency exceeds SLA, sudden drop in request volume (upstream failure), and memory/CPU saturation.

✓ Mentions the four golden signals, p95/p99 vs. averages, and structured logging. Bonus: OpenTelemetry or distributed tracing.
✗ "I look at the logs when something goes wrong" — purely reactive. No proactive alerting. Hallmark of someone who hasn't operated a production service.

› "Why is p95 latency more useful than average latency? Can you give me an example?" +
Expected Answer

The average (mean) can be misleading because it's heavily influenced by the majority of fast requests and masks the tail. Example: if 95% of requests complete in 50ms but 5% take 2 seconds, the average might be 150ms — which sounds fine. But 5% of your users are having a terrible experience, and those are often your heaviest users (whose requests trigger more complex processing).

p95 means "95% of requests are faster than this value." p99 is even more sensitive to outliers. SLAs are typically defined at p95 or p99 — "99% of requests will complete in under 200ms" — not at the average, because the average hides the worst user experiences.

The classic failure mode: a team monitors average latency, sees it's fine, and doesn't notice that a small percentage of users are timing out — until a major customer complains.

› "Tell me about a time an alert fired and you had to investigate — what was your process from alert to root cause?" +
Expected Answer

This is another "story" question — the answer quality varies, but the investigation process is what you're evaluating. A strong process: (1) Acknowledge the alert and check the dashboard to understand the scope — which endpoints? which regions? since when? (2) Check recent deployments — did anything go out in the last hour? If yes, that's the first suspect. (3) Drill into error logs filtered to the affected time window — look for patterns in error messages, user IDs, or request paths. (4) Check downstream dependencies — is the database healthy? Are any dependent services timing out? (5) Form a hypothesis, test it, and either roll back the deployment or apply a targeted fix.

A strong candidate can tell this story from memory with specifics. Someone who hasn't been on-call or operated production systems will give a vague, theoretical answer.

› "If you had to set up monitoring for a brand new API from scratch, what are the first three things you'd instrument?" +
Expected Answer

Priority order for a new API: (1) Error rate — a spike in 5xx errors is the most critical signal; instrument this first and set an immediate alert. (2) Request latency at p95/p99 — alerts when the API becomes slow for real users; set baseline during initial load testing. (3) Request volume with anomaly detection — alerts on both sudden spikes (possible abuse or upstream misbehavior) and sudden drops (possible upstream failure or deployment issue).

After those three, the next priorities are database query latency, memory and CPU utilization, and cache hit rate. Strong candidates also mention adding a synthetic monitor — an automated test that calls a health-check endpoint every minute from outside the system, so you know the API is reachable from the consumer's perspective, not just internally healthy.

Level 1 Baseline — Core API Concepts Anyone claiming API experience should nail these
01 Can you walk me through the difference between REST and RPC-style APIs? When would you choose one over the other? +
Expected Answer

REST is resource-oriented — model around nouns (/users/42), use HTTP verbs (GET, POST, PUT, DELETE), stateless responses. Standard for public-facing APIs.

RPC-style (gRPC, JSON-RPC) is action-oriented — call functions directly (GetUser(id=42)). Faster, binary protocol (Protocol Buffers), preferred for internal microservice communication where performance matters more than discoverability.

✓ Mentions trade-offs: REST = discoverability, RPC = speed and tight contracts. Bonus if they mention GraphQL as a third model.
✗ Can only define REST and has never considered alternatives — suggests shallow experience.
Follow-Up Probes Click any probe to see the expected answer
›"Have you personally used gRPC or GraphQL on a real project? What was the use case?"+
Expected Answer

Strong candidates have a real story. gRPC use cases: internal microservice communication where performance matters and both sides are under the same team's control — e.g., a recommendation engine calling a user service thousands of times per second. GraphQL use cases: client-driven queries where different consumers (mobile vs desktop) need different subsets of data and you want to avoid over-fetching — popularized by Facebook.

A weaker but acceptable answer: they haven't used either but can explain the theory and give the right use cases for each. The red flag is claiming expertise on a CV and then being unable to describe a real scenario.

›"In REST, what's the difference between PUT and PATCH — when would you use each?"+
Expected Answer

PUT is a full replacement — you send the complete representation of the resource, and the server replaces it entirely. If you omit a field, it gets overwritten with null/default. Use PUT when you always send the full object.

PATCH is a partial update — you send only the fields you want to change, and everything else stays the same. Use PATCH when clients typically update one or two fields at a time (e.g., changing a user's email without resending their entire profile). PATCH is more network-efficient and harder to accidentally corrupt data with, which is why it's preferred for most update operations in practice.

›"What does 'stateless' mean in REST, and why does it matter for scaling?"+
Expected Answer

Stateless means each HTTP request must contain all the information needed to process it — the server doesn't remember anything about previous requests from the same client. Session state, if needed, is stored client-side (in a JWT or cookie) or in a shared external store (Redis), not in the server process's memory.

This matters enormously for scaling: if the server held session state in memory, every request from a user would have to go to the same server instance ("sticky sessions"). With stateless design, any instance in the load balancer pool can handle any request — you can freely add or remove instances without affecting users. This is what makes horizontal scaling straightforward in REST APIs.

02 What HTTP status codes do you use most often in an API, and what's the difference between a 400 and a 422? +
Expected Answer

Common codes: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Entity, 429 Too Many Requests, 500 Internal Server Error, 503 Service Unavailable.

400 vs 422: 400 = malformed at the syntax level (invalid JSON). 422 = syntactically valid but semantically wrong (age field contains -5). FastAPI uses 422 for Pydantic validation failures.

✓ Distinguishes 400 vs 422 confidently and mentions 429 — signals production scale experience.
✗ Only knows 200/400/500 and treats all errors as 400.

›"What's the difference between 401 and 403 — when would you return each?"+
Expected Answer

401 Unauthorized means the request has no valid authentication — there's no token, the token is expired, or the token signature is invalid. The name is a bit misleading; it actually means "unauthenticated." The client should re-authenticate and retry.

403 Forbidden means the request is authenticated (we know who you are) but you don't have permission to perform this action. You're logged in but trying to access an admin endpoint or another user's data. Unlike 401, re-authenticating won't help — you simply don't have the required role or ownership.

A common mistake is returning 403 when you should return 404 — for example, when a user tries to access a resource they don't own. Returning 403 confirms the resource exists, which is an information leak. Returning 404 is safer in those cases.

›"When should you use 204 vs 200 for a successful operation?"+
Expected Answer

200 OK is used when there's a response body — the request succeeded and here is the data you asked for. 204 No Content is used when the operation succeeded but there is no response body — the most common case is a successful DELETE operation. You deleted the resource; there's nothing to return.

Using 204 correctly signals to clients that they should not try to parse a response body (which would fail). It's also slightly more efficient since no body is transmitted. A well-designed API uses 201 + Location header for POST (created a resource, here's where it lives), 200 for GET/PUT/PATCH (here's the updated data), and 204 for DELETE.

›"Have you ever had a disagreement with a teammate about which status code to use?"+
Expected Answer

This is a collaborative culture question as much as a technical one. Common real disputes: whether to return 404 or 403 when a user accesses a resource they don't own (security vs. transparency debate); whether an idempotent POST should return 200 or 201 when the resource already exists; whether validation errors should be 400 or 422.

A strong candidate has a genuine story, demonstrates that they care about getting it right, and resolved it by referencing the HTTP spec or an established API design guide (like Google's or Stripe's). The quality of the answer shows whether they engage thoughtfully with API design or just write what works and moves on.

›"Can you walk me through how Pydantic models work in FastAPI and why they matter?"+
Expected Answer

Pydantic models are Python classes that define the expected shape and types of data. In FastAPI, you define a Pydantic model as a request body schema, and FastAPI automatically: validates incoming request JSON against the model, raises a 422 with detailed field-level errors if validation fails, and generates the OpenAPI spec for that endpoint — all from the same class definition.

Example: a CreateUserRequest model with email: EmailStr, age: int, name: str. If a client sends age: "banana", FastAPI returns a 422 with a message explaining that age must be an integer — without you writing any validation code. This replaces a lot of boilerplate that Flask developers write manually (checking if fields exist, validating types, returning error messages).

Pydantic v2 (used in newer FastAPI versions) is also significantly faster than v1 due to a Rust-based core.

›"Have you ever had to migrate an API from one framework to another? What drove that decision?"+
Expected Answer

Common real-world migration scenarios: Flask to FastAPI for async support and automatic documentation (the most common migration today); Django monolith to a microservices architecture because the team needed independent scaling and deployment; Flask to DRF when the data model complexity grew beyond what plain Flask handled cleanly.

What matters is the decision-making process: they identified a concrete limitation (sync bottleneck, missing validation, poor docs), evaluated the migration cost, and made a deliberate trade-off. A strong candidate will also describe how they handled the migration without downtime — typically by running both versions in parallel, gradually routing traffic to the new service, then deprecating the old one.

›"What does FastAPI give you out of the box that you'd have to build yourself in Flask?"+
Expected Answer

FastAPI provides out of the box: automatic request validation via Pydantic (Flask requires marshmallow or WTForms); automatic OpenAPI/Swagger UI docs generated from type hints (Flask requires flask-smorest or similar); native async support with async def route handlers (Flask's async support is bolted on); dependency injection system for sharing logic like auth, DB sessions, and configuration across routes; and automatic serialization of Pydantic response models. In Flask, all of these require separate libraries, manual wiring, and are often inconsistently implemented across a codebase.

04 How do you handle authentication and authorization in an API you've built — not consumed? +
Expected Answer

Authentication (who are you?) vs Authorization (what are you allowed to do?). A true API engineer has implemented both:

  • JWT — stateless tokens validated on every request. Common in FastAPI with python-jose.
  • API Keys — for service-to-service. Stored hashed in DB, validated via X-API-Key header.
  • OAuth2 — delegated auth for third-party access.
  • RBAC — check user role against required permissions per endpoint.

In FastAPI, implemented via dependency injection — a get_current_user dependency applied per-route or globally.

✗ Only describes how to pass an API key when calling someone else's API — that's the consumer, not the builder.

›"What happens when a JWT expires — what's the flow from the client's perspective, and how did you handle refresh tokens?"+
Expected Answer

A JWT has an exp (expiration) claim. When it expires, the server rejects the request with a 401. Without refresh tokens, the user would have to log in again every time — a bad experience if the access token has a short lifetime.

The standard pattern: issue two tokens at login — a short-lived access token (e.g., 15 minutes) used on every API call, and a long-lived refresh token (e.g., 7–30 days) stored securely. When the access token expires, the client silently calls POST /auth/refresh with the refresh token to get a new access token — without interrupting the user. The refresh token is stored in an HttpOnly cookie (not accessible to JavaScript) to reduce XSS risk. On logout, the refresh token is revoked in the database.

The short lifetime of access tokens limits damage if one is stolen — it expires quickly. The refresh token is the higher-value credential and should be treated accordingly.

›"How do you store API keys securely — what would be wrong with putting them in plain text in a database?"+
Expected Answer

Storing API keys in plain text means a database breach immediately exposes all keys — an attacker can use every key without any further work. The same principle applies to passwords.

The correct approach: store only a one-way hash of the API key (using a secure algorithm like bcrypt or SHA-256 with a salt). When a client sends a key, hash the incoming value and compare it to the stored hash. You never store the original. This way, even if the database is compromised, the attacker gets hashes that can't be reversed into working keys.

The implication: once issued, an API key cannot be "viewed again" by the owner — it can only be regenerated. This is standard practice (Stripe, GitHub, AWS all work this way). Display the key only once at creation time and instruct the user to save it.

›"Can you give me a concrete example of authorization logic — not just 'is the user logged in,' but 'can this user see this specific record'?"+
Expected Answer

A concrete example: a loan document API where users can only access documents belonging to their own account. After authentication confirms the user identity, the authorization check is: fetch the document from the DB, then verify document.account_id == current_user.account_id. If not, return 404 (not 403 — returning 403 confirms the document exists). Admins bypass this check via a role check first.

This must be implemented per endpoint — there's no global shortcut. A common mistake is checking permissions at the route level ("does this user have the 'view_documents' role?") but forgetting to check at the object level ("does this user own this specific document?"). Object-level authorization must happen after the DB fetch, every time.

In FastAPI, this is typically done in a service layer function that takes the current user as a parameter and raises an exception if the check fails — keeping authorization logic centralized rather than scattered across route handlers.

Level 2 Production Depth — Design & Reliability Where data engineers typically start to struggle
05 Walk me through how you design API versioning. What problems does it solve and what are the trade-offs between URL vs header versioning? +
Expected Answer
  • URL versioning (/v1/users) — most common, visible, easy to route. Trade-off: URLs accumulate over time.
  • Header versioning (Accept: application/vnd.api+json;version=2) — clean URLs. Trade-off: harder to test, less discoverable.
  • Query param versioning (?version=2) — simplest, but bad practice.

Production engineer also mentions: support timeline for old versions, deprecation strategy (sunset headers), communicating breaking changes.

✓ Has a clear opinion from real experience. Mentions deprecation and consumer communication.
✗ Never thought about versioning — suggests internal one-off scripts only.

›"How do you communicate to consumers that a version is being retired? What's the process and timeline?"+
Expected Answer

A structured deprecation process: first, add a Sunset HTTP response header to all responses from the deprecated version — this is an RFC standard header containing the date after which the endpoint will be removed, allowing automated tooling on the client side to detect it. Second, add a Deprecation header pointing to the migration documentation.

Beyond headers: email or Slack notification to all registered API consumers with a clear migration guide and timeline (typically 3–6 months minimum for external consumers, shorter for internal). Monitor usage of the deprecated version and follow up with teams that are still calling it as the sunset date approaches. After the sunset date, return a 410 Gone status (not 404) for a grace period before fully removing the route.

A weak answer: "I just delete the old version" — this breaks consumers without warning and is a serious trust violation for an API product.

›"What counts as a 'breaking change'? Give me one obvious and two subtle examples."+
Expected Answer

Obvious breaking change: Removing a field from the response — any consumer reading that field will get a null or key error.

Subtle breaking change 1: Changing a field's type — e.g., changing user_id from an integer to a UUID string. The JSON still comes back, it still has the field, but consumer code that does arithmetic or integer comparisons on it will silently break.

Subtle breaking change 2: Changing the behavior of an existing endpoint — e.g., a search endpoint that previously returned all results now returns paginated results with a different response structure. Technically the field names might be the same but consumers that expected a flat array now get a paged object and break.

Non-breaking changes (safe to deploy without versioning): adding new optional fields to a response, adding new optional request parameters, adding new endpoints entirely.

›"Have you supported two active API versions simultaneously? How did you manage that in the codebase?"+
Expected Answer

Supporting multiple versions is one of the more painful parts of API engineering. Common strategies: (1) Separate route modules — routers/v1/users.py and routers/v2/users.py with shared business logic in a service layer that both call. Changes in v2 don't touch v1 code. (2) Response transformers — a single backend with version-specific serializers that transform the same data into v1 or v2 response shapes. (3) Feature flags — route to different code paths based on the version header or URL prefix.

The shared service layer approach is cleanest: both versions call the same underlying business logic, and versioning only affects the API contract (input/output shapes). This avoids duplicating business logic. The risk to watch for is "version creep" — where v1 and v2 business logic diverges over time because developers take shortcuts. Strong candidates mention code review discipline and integration tests for both versions in CI to prevent this.

›"Why does an in-memory rate limiter fail when you run more than one instance?"+
Expected Answer

If you store request counts in the application process's memory, each instance has its own independent counter. With a load balancer distributing traffic across 3 instances and a limit of 100 requests/minute, a single client could actually make 300 requests/minute — 100 to each instance — because each instance only sees one-third of their traffic and thinks the client is under the limit.

The fix is a shared, external store that all instances read from and write to atomically — Redis is the standard choice. Redis supports atomic increment-and-expire operations (using INCR + EXPIRE or the more sophisticated Lua scripting for sliding windows) that ensure the count is consistent across all instances regardless of which instance handles each request.

›"What's the difference between rate limiting by IP vs by API key — when would each be the right choice?"+
Expected Answer

Rate limiting by IP is useful before authentication — for login endpoints, signup, and public endpoints where API keys don't exist yet. It protects against brute-force attacks and unauthenticated abuse. Weakness: IP addresses can be spoofed or shared (corporate networks with NAT put thousands of users behind one IP), so IP-based limiting can be too coarse.

Rate limiting by API key is the right choice for authenticated endpoints. It's fair (each client gets their own quota regardless of where they connect from), auditable (you know exactly which client is hitting limits), and tier-able (different clients can have different limits based on their plan). Most production APIs combine both: IP-based limits for unauthenticated paths, API key-based limits for everything else, with a fallback to IP limiting for authenticated requests if the API key is somehow absent.

›"What does a good 429 response look like — what information do you include?"+
Expected Answer

A well-designed 429 response includes: the Retry-After header with the number of seconds until the client can retry (so they can back off intelligently rather than hammering the API); X-RateLimit-Limit — the total allowed requests in the window; X-RateLimit-Remaining — how many requests remain (ideally included on every response, not just 429s, so clients can proactively slow down); and X-RateLimit-Reset — Unix timestamp when the window resets.

›"What's a request ID and why is it useful — how do both the client and server benefit from it?"+
Expected Answer

A request ID is a unique identifier (typically a UUID) generated at the start of each API request and included in every log line for that request. It's returned to the client in a response header (e.g., X-Request-ID) and in the error response body when something goes wrong.

Server benefit: when an error occurs, all log lines for that specific request — across the entire processing chain — can be retrieved by filtering on the request ID. Without it, finding the relevant logs in a high-traffic API is extremely difficult.

Client benefit: when a consumer gets a 500 error, they can send the request ID to the API support team, who can immediately pull all logs for exactly that request without needing to know the user, endpoint, or approximate time. It transforms "something went wrong" into a specific, diagnosable event. In distributed systems with multiple services, the same request ID should propagate through all downstream calls — this is the foundation of distributed tracing.

›"Show me what a well-designed error response JSON looks like — what fields does it have and why?"+
Expected Answer

A well-designed error response has: error — a machine-readable error code (snake_case string like validation_error, resource_not_found, rate_limit_exceeded) that client code can switch on; message — a human-readable description of what went wrong; request_id — the unique ID for this request for support correlation; optionally field or details for validation errors (which specific field failed and why); and optionally a docs_url linking to relevant documentation.

The key principle: the error code is for machines, message is for developers, details is for form validation UIs, and request_id is for support. ›"What's the risk of returning a detailed Python exception message to an API consumer?"+
Expected Answer

Leaking exception details is a serious security vulnerability called information disclosure. A Python exception message can expose: the database host and port (from a connection error), table and column names (from a SQL error), file paths on the server (from a FileNotFoundError), library versions (from import errors), internal variable values, and the structure of the internal codebase. Each piece of information helps an attacker map the system and find exploitable weaknesses.

A specific real example: if your API returns psycopg2.OperationalError: could not connect to server: Connection refused — Is the server running on host "prod-db-internal.company.com" and accepting TCP/IP connections on port 5432? — you've just told an attacker your internal DB hostname and port. They now know you use PostgreSQL, the port, and the internal hostname, which can be used to probe the network from inside a compromised server.

08 Explain async vs sync endpoints in FastAPI — when would you use one over the other, and what mistake do people make with async? +

›"If you have no choice but to call a blocking synchronous library inside an async endpoint, what's the right way to do that?"+
Expected Answer

The correct approach is to use asyncio.run_in_executor(), which runs the blocking function in a thread pool executor — offloading it from the event loop so it doesn't block other requests.

In FastAPI specifically, you can use await asyncio.get_event_loop().run_in_executor(None, blocking_function, arg1, arg2). The None uses the default thread pool executor. For CPU-bound work (not just I/O-bound), you'd use a ProcessPoolExecutor instead to get true parallelism (since Python's GIL prevents real multi-threading for CPU work).

The cleaner long-term solution is to find an async equivalent of the library — e.g., replace psycopg2 (sync) with asyncpg (async), or replace requests (sync) with httpx (async). This eliminates the overhead of context switching to a thread pool entirely.

›"What happens to your API's throughput if one async endpoint accidentally calls a blocking function that takes 2 seconds?"+
Expected Answer

The event loop in Python is single-threaded. While a blocking call is executing inside an async def handler, the entire event loop is frozen — no other async requests can be processed, no timers fire, no I/O can complete. This means during those 2 seconds, all concurrent requests to any endpoint on that server instance are stalled and queuing up.

Under load, this creates a cascade: new requests arrive faster than the blocked event loop can process them, the request queue grows, connection timeouts start occurring, and the API appears completely unresponsive. A single misbehaving async endpoint can bring down an entire instance's throughput to near zero. This is why async Python code requires discipline — one mistake affects everyone using that server, not just the one request that caused it.

›"What's the difference between concurrency and parallelism, and which one does async/await give you?"+
Expected Answer

Concurrency means handling many tasks by switching between them — interleaving progress on multiple tasks, but only actually working on one at any given instant. Parallelism means actually doing multiple things simultaneously on multiple CPU cores.

Async/await gives you concurrency, not parallelism. The event loop switches between tasks at every await point — so while one request is waiting for a database query to return, another request can be served. But only one Python coroutine runs at any instant (due to the GIL). This is extremely efficient for I/O-bound work (where most time is spent waiting, not computing), but provides no benefit for CPU-bound work (image processing, ML inference, heavy computation) — for that you need multiple processes or a C extension that releases the GIL.

›"How do you handle the database in integration tests — do you use a real DB, a test DB, or mock it?"+
Expected Answer

›"What's a pytest fixture and how do you use it to avoid repeating setup code?"+
Expected Answer

A pytest fixture is a reusable setup function that pytest automatically injects into test functions that declare it as a parameter. It handles setup before the test and teardown after, without the test itself needing to manage that lifecycle.

Example: a db_session fixture that creates a test database session and rolls it back after each test. Any test that needs a DB session just lists db_session as a parameter — pytest handles the rest. A client fixture creates a FastAPI TestClient configured to use the test DB. A auth_headers fixture creates a test user and returns a valid JWT header. Tests compose these: def test_get_user(client, auth_headers, db_session) — clean, readable, no repeated setup code.

Fixtures have scope: function (default, run fresh for each test), module (once per file), session (once per entire test run). Use session-scoped fixtures for expensive setup like creating the test DB schema; use function-scoped for per-test state like creating test data.

›"What percentage of test cases should test error paths vs the happy path, and why?"+
Expected Answer

›"What's an N+1 query problem — can you give me a concrete example?"+
Expected Answer

The N+1 problem occurs when code fetches a list of objects (1 query), then makes an additional DB query for each object in the list (N queries) — resulting in N+1 total queries instead of 1 or 2.

Concrete example: An endpoint returns a list of loan documents with their associated borrower names. The naive implementation: (1) SELECT * FROM documents LIMIT 100 — 1 query returning 100 documents. Then for each document: (2–101) SELECT name FROM borrowers WHERE id = ? — 100 individual queries. Total: 101 DB round-trips instead of 1 JOIN.

Fix: use a JOIN or eager loading — SELECT documents.*, borrowers.name FROM documents JOIN borrowers ON documents.borrower_id = borrowers.id LIMIT 100 — fetches everything in 1 query. In SQLAlchemy ORM: use joinedload() or selectinload() rather than lazy loading. N+1 is extremely common and can turn a 50ms endpoint into a 5-second endpoint as the data grows.

›"Why is 'add more servers' not a complete solution to a performance problem?"+
Expected Answer

Adding more server instances increases capacity — the ability to handle more concurrent requests — but it doesn't reduce the time any individual request takes. If a single request is slow because it makes 100 DB queries, adding 3x more servers means 3x more slow requests can run concurrently, not that each request is faster. The DB is now getting 3x more load from those N+1 queries, which makes it slower for everyone.

Horizontal scaling solves saturation — you're running out of server capacity to handle the volume. It doesn't solve inefficiency — a request that's slow because of bad code stays slow regardless of how many servers you add. Worse, some inefficiencies get amplified by adding servers (more DB connections, more cache misses if not properly partitioned). Fix the code first; scale when the fixed code still can't keep up with legitimate traffic volume.

›"Say you add a Redis cache to a slow endpoint. What risks does that introduce, and how do you manage them?"+
Expected Answer

Caching introduces stale data as the primary risk — the cache serves an old version of the data after the underlying record has been updated. Management strategies: (1) TTL (time-to-live) — data expires automatically after N seconds; accept some staleness in exchange for simplicity. (2) Cache invalidation — explicitly delete or update the cache entry whenever the underlying data changes. More complex but keeps data fresh. (3) Cache-aside pattern — the app checks the cache first; if miss, fetches from DB and populates the cache. Gives the app full control.

Additional risks: cache stampede — when a popular cache entry expires, many requests simultaneously hit the DB before the cache is repopulated. Fix with mutex locks or probabilistic early expiration. Cache inconsistency in multi-instance deploys — if cache is in-memory, different instances serve different data. Fix by using a shared external Redis. Redis becoming a single point of failure — if Redis goes down and your code doesn't have a cache-miss fallback, the API fails entirely. Always code defensively: treat a cache miss as normal, fall back to the DB.

›"What's the difference between polling and webhooks from the consumer's perspective — when is each better?"+
Expected Answer

Polling — the client repeatedly calls GET /jobs/{id} until the status is complete. Simple for the consumer to implement (just a loop with a sleep), works behind firewalls, and doesn't require the consumer to expose any endpoints. Downside: wastes requests during the waiting period, and the polling interval creates latency (if you poll every 5 seconds, you may not know the job is done for up to 5 seconds after completion).

Webhooks — the API calls back to the consumer's provided URL when the job is done. More efficient (zero wasted requests), real-time notification, but requires the consumer to run an HTTP server that can receive POST requests — which may not be possible behind firewalls or from CLI tools. Also requires the consumer to handle webhook security (verify the request came from your API, not a spoofed source) and implement retry handling if their webhook endpoint was temporarily down.

Rule of thumb: use polling for simple integrations, internal tooling, and cases where consumers may not have a public endpoint. Use webhooks for consumer-facing APIs with SLA requirements and where real-time notification has real value (payment confirmations, document processing results).

›"What happens to a queued job if your worker crashes halfway through?"+
Expected Answer

This is where task queue reliability design matters. The key concept is message acknowledgment: a message in the queue is not deleted until the worker explicitly acknowledges successful completion. If the worker crashes, the message stays in the queue (or returns to it after a visibility timeout) and gets picked up by another worker instance — providing at-least-once delivery.

Design implications: jobs must be idempotent — running the same job twice must produce the same result as running it once. This is non-trivial if the job writes to a DB or calls an external API. Techniques: store a job completion flag in the DB and check it before processing; use idempotency keys when calling external APIs.

For permanently failing jobs (exceeded max retries), they go to a dead letter queue (DLQ) — a separate queue where failed messages accumulate for manual inspection and potential reprocessing. Monitoring the DLQ size is an important operational metric: a growing DLQ means jobs are systematically failing and needs investigation.

›"How do you set up a task queue — what are the moving parts?"+
Expected Answer

The main components: (1) Message broker — stores the queue of pending jobs. Options: Redis (simple, fast, built-in Celery support), RabbitMQ (more robust, supports complex routing), AWS SQS (managed, integrates with AWS ecosystem). (2) Worker processes — separate Python processes that run independently of the API server. They pull jobs from the queue and execute them. Run with Celery (celery -A app worker). Can be scaled horizontally by running more worker instances. (3) Task definitions — Python functions decorated with @celery.task that define what happens when a job runs. (4) Result backend — stores job status and results (Redis or DB) so the API can answer status poll requests. (5) Monitoring — Flower (Celery's web UI) or custom metrics to watch queue depth, worker health, and job failure rates.

The API server and workers are completely separate processes — the API's only job is to enqueue tasks and read their status; it never executes long-running work itself.

›"Why does a large UPDATE on a table cause downtime, even if the API is still running?"+
Expected Answer

When PostgreSQL (or most relational databases) executes a large UPDATE or ALTER TABLE ... ADD COLUMN NOT NULL operation, it acquires a lock on the table for the duration. Other transactions that need to write to (or in some cases read from) that table must wait until the lock is released. For a migration that touches millions of rows, this lock can be held for seconds or minutes.

During that time, API requests that try to read or write the affected table either queue up (causing latency spikes and timeouts) or fail outright. This looks like a full API outage from the user's perspective even though the application server is running fine.

The safe alternative for large data changes: add the column as nullable first (no lock needed for nullable columns in Postgres), backfill in batches of a few thousand rows at a time using a background script, then add the NOT NULL constraint after all rows are populated (Postgres can often do this without a full table scan if the column has been populated). This spreads the load over minutes or hours rather than causing one concentrated lock event.

›"What's a rollback script and why do you need one before running a migration?"+
Expected Answer

A rollback script is the reverse of the migration — the SQL or Alembic commands that undo the schema change if something goes wrong after deployment. In Alembic, each migration file has both an upgrade() function (apply the change) and a downgrade() function (reverse it).

You need a tested rollback because: deployments fail. If you run a migration, discover the new API version has a bug, and need to roll back to the previous code version — the database schema and the code version must be compatible. If you rolled back the code but can't roll back the schema, you're stuck with a schema the old code doesn't understand.

Critical practice: test the downgrade path in staging before every production migration. Many teams only write the upgrade and discover the downgrade is broken only when they urgently need it at 2am. A rollback that doesn't work is the same as no rollback.
